<summary><h4>화면이 갑자기 하얗게 죽어버렸는데, 범인은 유튜브였어요</h4></summary>

> **문제**: 찬양 릴스에 배경 음악을 재생하려고 YouTube IFrame API를 붙였는데, 처음엔 가장 자연스러운 방식대로 React가 렌더링한 `<div ref={containerRef}>`를 그대로 `new YT.Player()`의 타겟으로 넘겼어요. 그런데 이 API는 넘겨받은 타겟 DOM을 통째로 `<iframe>`으로 바꿔치기하는 부작용이 있었고, React의 가상 DOM은 여전히 `<div>`가 있다고 믿는데 실제 DOM은 `<iframe>`으로 바뀌어 있으니, 다음 리렌더링이나 언마운트 시점에 React가 자기가 그렸던 노드를 찾지 못하고 `insertBefore`/`removeChild` NotFoundError를 던지며 화면이 하얗게 죽었어요. 보통은 `react-youtube` 같은 래퍼 라이브러리 뒤에 가려져 잘 드러나지 않는, IFrame API를 직접 다룰 때만 마주치는 문제였어요.

> **해결**: "YouTube가 내가 렌더링한 DOM을 React 몰래 바꿔치기한다"는 원인을 짚어낸 뒤, 타겟 div를 아예 React 렌더링 흐름 밖에서 만드는 방식으로 바꿨어요. 순서는 이래요. 1) React는 빈 wrapper `<div ref={wrapperRef}>`만 렌더링하고 그 안에는 어떤 자식도 그리지 않아요. 2) 컴포넌트가 마운트되면 `wrapperRef.current`에 `document.createElement('div')` + `appendChild`로 자식 div를 직접 심어요 — JSX가 아니라 순수 DOM API 호출이라, React의 가상 DOM 트리에는 이 자식이 기록조차 되지 않아요. 3) `new YT.Player()`에는 이 수동 생성 div를 타겟으로 넘겨요. YouTube가 이걸 `<iframe>`으로 바꿔치기해도, React 입장에선 애초에 몰랐던 노드라 다음 리렌더링 때 비교할 "이전 상태"가 없으니 충돌이 날 수가 없어요. 4) 언마운트 시엔 React의 클린업이 wrapper를 지우기 전에, `while (wrapper.firstChild) wrapper.removeChild(wrapper.firstChild)`로 wrapper의 자식들을 먼저 수동으로 비워서, React가 마지막으로 기억하는 "wrapper는 비어있다"는 상태와 실제 DOM을 다시 맞춰놨어요. 레시피를 찾아 적용한 게 아니라 "React가 아예 모르는 영역을 의도적으로 만든다"는 원리부터 스스로 추론해 해결한 좋은 경험이였어요

<summary><h4>"느리다" 한 마디에 원인이 몇 개나 숨어있었을까요</h4></summary>

> 사용자에게는 그냥 "느리다"는 감각 하나지만, 실제로는 레이어마다 전혀 다른 원인이 겹쳐 있었어요. "최적화했다"고 뭉뚱그리는 대신, 어느 레이어에서 왜 지연이 나는지부터 하나씩 분리해서 진단한 뒤 레이어에 맞는 해법을 따로 적용했어요.

| 지연 유형 | 증상 | 실제 원인 | 해결 |
|---|---|---|---|
| 서버 응답 지연 (TTFB) | 첫 진입 자체가 느림 | 매 요청 동적 렌더링 | force-static + Server Component 전환 |
| 네트워크 과다 요청 | 큐레이션 열 때마다 버벅임 | 필요한 양(300bytes)보다 2,800배 큰 페이로드(840KB) | Batch API로 요청을 1회로 압축 |
| 반복 방문 지연 | 재방문해도 매번 다시 느림 | 같은 UID 조합인데도 매번 서버까지 왕복 | Service Worker CacheFirst 30일 캐싱 |
| 리렌더링 지연 | 오디오 재생 한 번에 화면 4개가 같이 흔들림 | 필요 이상으로 넓은 범위의 상태 구독 | 실제 사용처로 구독 범위 축소 |
| 번들 크기 지연 | 안 쓰는 페이지까지 초기 진입이 무거움 | 큐레이션 40여 개가 전부 정적 import로 번들에 포함 | 네이밍 컨벤션 기반 동적 import로 전환, 번들 60KB 감소 |
| 체감 지연 | 실제 지연은 그대로인데 "반응이 없다"고 느껴짐 | 지연 자체가 아니라 지연 동안 피드백 부재가 문제 | 클릭 즉시 시각 피드백(`useTransition`), 드래그 시작 시점 프리페치, 스켈레톤 UI로 대기 숨김 |

> 표의 TTFB·Batch API·SW 캐싱·리렌더링 최적화는 아래 각 항목에서 구체적인 수치와 구현으로 이어져요. 번들 최적화와 체감 지연은 "진짜 지연을 줄이는 것"과 "지연을 못 느끼게 하는 것"이 서로 다른 문제라는 걸 보여주는 사례라 여기서 함께 짚었어요.

<summary><h4>1초 넘게 걸리던 첫 로딩, 30ms까지 줄인 방법은요</h4></summary>

> **문제**: 페이지가 매 요청마다 서버리스 함수로 동적 렌더링돼 TTFB(첫 바이트 응답 시간)가 Netlify 기준 1,134ms까지 걸렸어요.

> **해결**: 한 번에 해결되지 않아서 원인을 좁혀가며 세 단계로 나눠 잡았어요. 
> 1) Next.js가 정적 최적화를 위해 공식 제공하는 `export const dynamic = 'force-static'`을 먼저 전체 페이지에 붙였는데, Netlify가 App Router의 `force-static`을 완전히 지원하지 않아 579ms(48% 개선)에서 더 줄지 않았어요. 
> 2) 사실 Netlify는 애초에 "Vercel보다 무료 플랜 bandwidth가 넉넉하다(월 100GB)"는 이유로 일부러 골랐던 플랫폼이었는데, 정작 성능에 필요한 App Router 정적 최적화 지원은 Next.js 공식 플랫폼인 Vercel보다 약하다는 게 발목을 잡았어요. 그래서 bandwidth 제한이 더 빡빡해지는 걸 감수하고 배포 플랫폼을 Vercel로 옮겼고, 265ms(4배)까지 줄었지만 응답 헤더는 여전히 `x-vercel-cache: MISS`라 CDN 정적 캐싱은 안 되고 있었어요. 
> 3) 원인을 파보니 동적 라우트(`[[...slug]]`)의 `page.tsx`가 `'use client'`로 선언돼 있어서, `force-static`을 붙여도 Next.js가 이걸 Server Component로 인식하지 않아 정적 최적화 대상에서 제외되고 있었어요. `'use client'`를 제거해 Server Component로 전환하고, styled-components를 쓰던 로딩 폴백만 별도 Client Component로 분리, `useSearchParams`를 쓰는 `ContentRouter`는 `<Suspense>` 경계로 감싸서 충돌 없이 재구성했어요.

> **결과**: 빌드 출력에서 `/[[...slug]]`가 `○ (Static)`으로 분류되어 CDN에서 정적 서빙되기 시작했고, TTFB는 1,134ms → 579ms → 265ms → 약 30ms(최대 35배)까지 줄었어요.

</details>

> `react-use-gesture`는 성능을 위해 `passive: true`가 고정돼 있어 `preventDefault()` 자체가 불가능했고(iOS 시스템 제스처를 막을 방법이 없어요), `framer-motion`의 제스처 기능은 애초에 "Safari 엣지 스와이프 차단" 같은 케이스를 다루지 않았고, `hammer.js`는 PWA standalone 모드 감지가 안 돼서 "브라우저로 볼 때"와 "홈 화면에 설치해서 볼 때"를 구분할 방법이 없었어요.

> **해결**: 그래서 `useCardGestures`(탭·더블탭·롱프레스·스와이프업)와 `usePeekSwipe`(엣지 스와이프)를 라이브러리 없이 직접 구현했어요. 엣지 40px 이내에서 시작하는 스와이프만 감지하고, 20px 이상 움직여야 액션이 실행되게 하면서 그 사이는 진행 거리에 비례해 opacity를 점진적으로 올려 "지금 당기고 있다"는 시각 피드백을 줬어요.

> 탭은 인스타그램 스토리처럼 화면을 좌/우로 나눠 이전/다음 페이지로 연결했고(카드 실측 폭 기준 정확히 50/50 분할), 더블탭(300ms 이내 재탭)과 롱프레스(500ms)는 이동거리 10px 이내인지로 구분해 서로 오인식하지 않게 만들었어요.

> 애니메이션까지 전부 손으로 짤 필요는 없어서, 제스처 "인식"만 직접 만들고 인식 후 보여주는 애니메이션은 Framer Motion에 맡겨 역할을 나눴어요.

> **결과**: 라이브러리 없이 네 가지 제스처가 충돌 없이 공존, `react-use-gesture` 미사용으로 번들 크기 약 13KB 절약.

<summary><h4>터치는 착 붙는데, 마우스 휠은 왜 따로 코드를 짜야 했을까요</h4></summary>

> **문제**: 릴스처럼 카드 단위로 딱 맞춰 멈추는 느낌을 CSS `scroll-snap-type: y mandatory` + `scroll-snap-align: start` + `scroll-snap-stop: always`로 구현했어요. 터치 스와이프에서는 잘 맞았지만, 마우스 휠로 빠르게 여러 번 스크롤하면 두 카드 사이 중간 위치에서 스크롤이 멈춰버리는 문제가 있었어요. `scroll-snap-stop: always`가 슬라이드를 강제로 멈추려는 것과, 브라우저의 가속도 기반 휠 스크롤·`scroll-behavior: smooth`가 서로 경쟁하면서 생기는 충돌이었어요.

> **해결**: CSS snap 자체는 그대로 두고, `wheel` 이벤트만 JS로 완전히 가로챘어요. `preventDefault()`로 브라우저 기본 스크롤을 차단한 뒤 `deltaY` 부호로 방향만 읽어서 `container.scrollTo({ top: nextIndex * clientHeight, behavior: 'smooth' })`로 정확히 카드 한 장만큼만 이동시켰어요. 이전 스크롤 애니메이션이 끝나기 전(약 400ms)의 추가 휠 입력은 무시해서, 휠을 연속으로 굴려도 한 번에 한 장만 넘어가게 했어요. 결과적으로 터치는 CSS snap 그대로 쓰고 마우스 휠만 JS로 별도 제어하는, 입력 방식별로 다른 레이어에서 처리하는 구조가 됐어요.

> **결과**: 마우스 휠 중간 멈춤 현상 완전 제거, 터치·키보드 동작은 기존 그대로 유지.

</details>

<summary><h4>iOS 시스템 제스처랑 충돌하던 스와이프, 라이브러리 없이 어떻게 잡았을까요?</h4></summary>

> **문제**: iOS PWA(Standalone 모드)에서 화면 좌측 엣지 40px 이내 스와이프가 시스템 뒤로가기 제스처로 인식돼, 앱의 커스텀 스와이프와 충돌했어요.

> **해결**: `touchstart`에서 터치 시작 좌표가 엣지 영역인지 확인해 `preventDefault()`로 시스템 제스처를 차단했어요. iOS는 `{ passive: false }` 옵션 없이는 `preventDefault`가 무시돼서 이를 반드시 지정했고, `navigator.standalone`/`matchMedia('(display-mode: standalone)')`로 iOS PWA 환경에서만 동작하도록 범위를 좁혔어요.

<details>
<summary><h4>번역본 5개, 언어도 여러 개인데 API 호출 수는 어떻게 줄였을까요?</h4></summary>

> **문제**: 성경 데이터는 번역본별로 66권짜리 JSON(책 하나당 파일 하나)으로 저장돼 있어요. 평독 모드처럼 한 장을 순서대로 읽을 땐 이 구조로 충분했지만, 큐레이션·홈피드·북마크·Topics처럼 서로 다른 책에 흩어진 구절 몇 개만 필요한 "랜덤 접근" 상황에서는 `loadVerses()`가 구절 하나를 위해서도 그 구절이 속한 책 전체를 통째로 import했어요.

> 큐레이션 하나("소망의 빛")가 로마서·예레미야·시편에서 딱 3구절(300bytes)만 쓰는데 실제로는 책 3권(840KB)을 통째로 내려받는 식이었고, 비슷한 과다 다운로드가 Topics 페이지(10구절, 500배), 홈 구절 릴스(1구절, 500배), 북마크(3구절, 667배)에서도 반복됐어요.

> **해결**: 이 비효율을 줄일 방법을 4가지로 나눠 검토했어요. A) 장 단위로 파일을 쪼개기(66권→1,189개 장) — 840KB→12KB(70배)까지는 줄지만 여전히 40배 과다였고, HTTP 요청 횟수(왕복 시간)는 그대로였고, 파일이 5,940개로 늘어나는 관리 부담이 있었어요. B) 절 단위로 쪼개기(31,102개 구절) — 5개 번역본 기준 파일이 15만 개를 넘고, HTTP 헤더(500bytes)가 실제 데이터(100bytes)보다 커지는 역전 현상까지 있어서 바로 제외했어요. C) 필요한 구절 UID만 서버에서 추출해 응답하는 Batch API — 이걸 채택했어요. D) 큐레이션 JSON에 텍스트를 미리 박아넣기 — 840KB→5KB(168배)까지 줄지만 번역본이 바뀔 때마다 데이터를 다시 구워야 해서, 오프라인 폴백 용도로만 남겨뒀어요.

> 채택한 Batch API(`GET /api/verses?uids=...&version=...`)는 구절 UID 배열을 한 번에 받아 요청을 1회로 합치고, 서버가 `fs.readFileSync`로 필요한 책만 로컬 SSD에서 읽어(1ms) 요청받은 구절만 추출해 응답해요.

> 캐싱은 3단계로 쌓았어요. 클라이언트 메모리 Map(같은 구절 재요청 시 0ms), HTTP 브라우저 캐시(`Cache-Control` 1년, 같은 요청이면 서버까지 안 감), 서버 메모리 캐시(같은 책의 다른 구절을 요청해도 파일 I/O가 다시 안 일어남) 순서예요. 번역본 5개(KRV, NKRV, KJV, YLT, WEB)를 오가도 데이터가 어긋나지 않도록, 특정 번역본에 종속되지 않는 전역 UID로 구절을 식별해서 캐시 키를 통일했어요.

> 이 구조는 큐레이션 하나에만 적용한 게 아니라 홈피드·북마크·마이 큐레이션·이어읽기·읽기표(잠언·시편)까지, 구절을 "랜덤하게" 가져오는 6개 기능 전부를 Batch API로 옮겼어요. 반대로 평독 모드처럼 순서대로 읽는 화면은 그대로 장 단위 Dynamic Import + 인접 장 프리페칭을 유지해서, 접근 패턴이 다르면 로딩 전략도 다르게 가져간다는 원칙을 지켰어요.

> **결과**: 큐레이션 1개 840KB→300bytes(2,800배), 큐레이션 10개 4MB→3KB(1,333배), Topics 페이지 500KB→1KB(500배), 응답 시간 250ms→50ms.

</details>

<summary><h4>같은 구절을 또 열었는데, 두 번째부터는 서버를 아예 안 탔어요</h4></summary>

> **문제**: `/api/verses`가 이미 CDN에 캐싱되고 있었지만, 새로운 UID 조합일 때마다 서버리스 함수의 cold start(약 100~200ms)가 매번 발생했어요.

> **해결**: Service Worker에 `CacheFirst` 전략을 추가해 자주 쓰는 UID 조합을 30일간 캐싱했어요. `homeStore`가 홈 피드 상태를 localStorage에 저장해두는 덕분에 재방문 시 같은 UID 조합이 보장되고, 성경 데이터는 불변이라 30일 캐싱이 안전했어요.

> **결과**: 재방문 시 구절 로딩 약 0ms.

</details>

<details>
<summary><h4>화면 전환할 때 깜빡임이 한 번도 없었던 이유, 사실 페이지 이동을 안 했어요</h4></summary>

> **문제**: Next.js 파일 기반 라우팅으로 홈/릴스/평독 사이를 이동하면 컴포넌트가 매번 언마운트·리마운트돼 화면이 깜빡이고, 이미 불러온 데이터도 재사용할 수 없었어요. 책을 덮고 다른 책을 펴는 것과 같았어요.

> **해결**: `ContentRouter`가 **스와이프 전환이 필요한 뷰(홈·릴스·평독·주제별)만** 전부 항상 마운트해두고, `view`/`back` URL 파라미터만으로 전환과 스마트 백내비게이션을 관리하게 했어요. 반대로 탐색·북마크·설정처럼 독립적인 화면은 통합하지 않고 그대로 뒀어요. 여러 뷰를 항상 메모리에 들고 있어야 하는 트레이드오프는 의도적으로 감수했어요.

> 실제 전환 방식은 캐러셀과 같은 원리예요. `ReaderViewLayers`가 4개 뷰를 전부 고정 위치 레이어로 동시에 마운트해두고, 활성 뷰만 `translateX(0)`으로 화면에 두고 나머지는 `translateX(100vw)`로 화면 밖에 밀어놔요 — 뷰를 새로 그리는 게 아니라 이미 그려진 레이어들의 위치만 옆으로 밀어서 전환하는 거예요. 화면 밖에 있는 비활성 레이어가 클릭이나 스크롤을 가로채지 않도록 `pointer-events`와 `z-index`도 뷰별로 따로 관리했고, 슬라이드 애니메이션(0.3초)이 끝난 뒤에야 새로 활성화된 뷰가 클릭을 받도록 살짝 지연(0.31초)을 줬어요.

> **결과**: 화면 깜빡임 없이 전환 시간 16ms.

> 같은 "화면을 유지한 채 필요한 것만 갈아 끼운다"는 원칙은 홈 피드의 무한 스크롤에도 적용돼요. `homeStore`는 진입 시 1개를 즉시 로드해 로딩 화면부터 빠르게 걷어낸 뒤, 백그라운드로 사용자의 콘텐츠 패턴 길이만큼(기본 설정 기준 10개)과 배치 10개를 추가로 채워 초기 피드를 두툼하게 만들어요.

> 이후 스크롤 중엔 남은 카드 수가 5개 이하로 줄어들 때마다 다음 10개를 백그라운드로 미리 불러와요. 이 조건은 카드가 전환될 때마다 체크하는 경로와 스크롤이 끝에 가까워졌을 때 감지하는 경로, 두 곳에서 동시에 걸려 있어서 사용자가 스크롤을 멈추지 않아도 항상 다음 데이터가 준비돼 있어요.

> 다만 무한정 쌓이면 메모리를 계속 먹으니, 전체 아이템 수가 40개를 넘으면 오래된 앞쪽 아이템부터 잘라내고 현재 보고 있는 인덱스도 그만큼 같이 보정해요. 다만 카드 렌더링 자체는 DOM 가상화 없이 로드된 아이템을 전부 마운트하는 구조라, 이 40개 상한은 "메모리 상한"이지 "렌더링 최적화"는 아니라는 것도 정확히 구분해요.

</details>

<details>
<summary><h4>성경 구절, 헬라어, 찬양, 기도문... 형태가 다 다른데 왜 한 화면에서 매끄럽게 넘어갈까요?</h4></summary>

> **문제**: 큐레이션 콘텐츠가 구절·헬라어·찬양가사·미디어·묵상·암송퀴즈·이벤트·읽기진행도처럼 형태가 전부 달라서, 각각 다른 렌더링 로직을 만들면 화면마다 UX가 제각각이 될 위험이 있었어요.

> **해결**: `Page`를 9종 타입(구절·텍스트·헬라어·가사·미디어·묵상·읽기진행도·암송퀴즈·이벤트)의 discriminated union으로 설계하고, `PageRenderer`가 `page.type`으로 분기해 타입별 컴포넌트에 위임하는 strategy 패턴으로 렌더링하게 했어요. 새 타입을 추가할 때 손대는 곳을 "타입 정의 1곳 + `PageRenderer` 분기 1곳"으로 고정해서, 이미 있는 타입들의 렌더링 로직은 절대 안 건드리게 만들었어요. 사전 제작된 정적 큐레이션과, 사용자 진행도·날짜 기반으로 실시간 생성되는 동적 큐레이션(이어읽기, 오늘의 잠언·시편, 마태·마가·누가·요한·사도행전·바울서신 등 465개 이상의 소제목 순차 읽기)도 같은 파이프라인에 통합했어요.

> 페이지 사이 전환은 화면 탭 위치로 이뤄져요. 탭 좌표를 카드의 실제 렌더 폭(`getBoundingClientRect`) 기준으로 좌/우 절반으로 나눠 이전/다음 페이지를 판정하는데, `window.innerWidth`가 아니라 카드 자신의 실측 폭을 기준으로 삼은 건 데스크톱처럼 카드가 화면 전체 폭이 아닐 수 있는 레이아웃까지 고려한 거예요. 페이지가 여러 장인 콘텐츠에는 인스타그램 스토리 같은 상단 진행 바(`PageIndicator`)가 뜨고, 암송 퀴즈처럼 다음 페이지로 넘어가기 전에 조건이 있는 경우엔 `isPageLocked`로 페이지 이동 자체를 막아요.

> 페이지 전환 상태 갱신은 `startTransition`으로 감싸서 낮은 우선순위 업데이트로 처리했어요 — 무거운 `PageRenderer` 리렌더링이 탭 응답성을 막지 않게 하기 위해서예요.

> **결과**: 새 콘텐츠 타입을 추가해도 기존 화면은 안 건드림, `startTransition` 적용으로 탭 즉시 반응성 유지.

</details>

<details>
<summary><h4>혼자 만든 프로젝트인데 왜 이렇게까지 규칙을 정했을까요?</h4></summary>

> **문제**: 기능이 늘어날수록 `isActive`, `onChange`처럼 이름만 봐서는 무슨 의미인지 알 수 없는 props가 쌓이기 쉬웠고, 레이어 간 의존 방향도 흐트러지기 쉬웠어요.

> **해결**: boolean props는 `is`/`should`/`has` 접두사, 콜백은 `on + 명사 + 동사` 패턴을 강제하는 네이밍 규칙을 세웠어요. `features → shared`만 허용하고 반대 방향은 금지하는 단방향 레이어 규칙을 두고, 위반이 필요한 경우 항상 props로 주입하게 했어요. 코드를 나중에 AI 도구로 다시 훑어봐도 이름만으로 의도가 파악되게 하는 것도 목표였어요.

> **결과**: 100개 넘는 파일에서 일관된 구조 유지, 처음 보는 사람도 이름만으로 의도 파악 가능.

</details>

<details>
<summary><h4>AI한테 코드 정리를 맡겼는데, 진짜 작업은 정리가 아니었어요</h4></summary>

> **문제**: 100개 넘는 파일에 JSDoc·코드 순서·섹션 구분선을 일관되게 정리하는 작업을 AI 도구에 맡기려 했는데, 그냥 "정리해줘"라고만 시키면 위험이 두 가지 있었어요. AI가 "더 낫다"고 판단해서 기존 인라인 주석을 지우거나 로직까지 슬쩍 바꿔버릴 수 있다는 것, 그리고 파일 수가 많다 보니 한 번에 다 맡기면 중간에 타입이 깨져도 어디서부터 잘못됐는지 추적하기 어렵다는 것이었어요.

> **해결**: 그래서 "무엇을 정리할지"보다 "AI가 하면 안 되는 것"부터 문서로 못박았어요. 기존 인라인 주석 삭제 금지, 로직 변경 금지, 이미 잘 동작하는 코드 리팩토링 금지를 명시하고, 작업 전엔 반드시 `git diff`로 원본 주석 상태를 먼저 확인하게 했어요.

> 작업 순서도 의존성 방향으로 고정했어요. 의존성이 없는 `utils`부터 `core → features → components → app` 순서로 진행하고, 배치당 파일 4~6개만 건드리게 한 뒤 매 배치마다 `tsc --noEmit`으로 타입 체크를 통과해야 다음 배치로 넘어가게 했어요. 같은 디렉토리 안의 파일들은 서로 의존하지 않으니 병렬로 맡겨도 안전하다는 판단까지 문서에 남겨뒀고요.

> 이 문서는 사람이 읽는 가이드가 아니라, 맨 위에 "이 문서를 프롬프트로 사용하여 새 채팅에서 코드 정리를 진행할 수 있습니다"라고 적어둔, AI에게 그대로 복사해 붙여넣는 작업 지시서였어요.

> **결과**: 100개 넘는 파일에 일관된 JSDoc·코드 순서·주석 보존 규칙을 적용, 배치별 타입 체크로 중간에 깨지는 지점 없이 안전하게 완료.

</details>


<details>
<summary><h4>번역본을 더블탭 하나로 바로 바꿀 수 있는 이유</h4></summary>

> **문제**: 번역본(한국어 2종·영어 3종)을 전환할 때마다 새로 API를 호출하면 전환이 끊기고 느리게 느껴져요. 그리고 이 프로젝트는 화면마다 언어를 따로 설정하지 않고, 지금 보던 큐레이션에서 영어로 바꾸면 홈·북마크 등 앱 전체가 영어 성경으로 바뀌는 전역 일관성을 원칙으로 삼았어요 — 페이지별로 언어가 따로 노는 게 오히려 혼란을 준다고 판단했거든요. 다만 언어 전환의 범위는 성경 구절·책 이름·참조 표시로만 한정했고, 버튼·메뉴 같은 UI 텍스트와 큐레이션 타이틀은 한글을 유지해서 "앱 전체 번역"이 아니라 "성경 읽기 모드 전환"에 가깝게 의도적으로 좁혔어요.

> **해결**: 더블탭으로 한/영을 전환하는 UX를 만들면서, 홈 피드에 새 콘텐츠가 로드될 때마다 그 안의 구절·큐레이션·기도문 전부에 대해 반대 언어 버전을 자동으로 백그라운드에서 미리 불러와 뒀어요. 더블탭하는 순간엔 이미 캐시에 있는 데이터를 쓰기 때문에 네트워크를 안 타고, 아직 프리로드가 안 끝난 콘텐츠라면 그 자리에서 해당 언어 데이터를 로드하는 폴백도 뒀어요.

> **결과**: 캐시 히트 시 더블탭 즉시 전환(대기 시간 없음), 캐시 미스여도 100~300ms 안에 로드 완료.

</details>

<details>
<summary><h4>기능이 계속 늘어나도 안 얽히게, 미리 선을 그어둔 게 있어요</h4></summary>

> **문제**: 기능이 늘어날수록(홈 피드, 성경 읽기, 큐레이션, 오디오, 탐색, 제작 도구 등) 컴포넌트·상태·로직이 서로 뒤엉키기 쉬웠고, 특히 여러 기능이 같은 공용 UI 컴포넌트를 가져다 쓰다 보면 "이 컴포넌트가 어떤 기능의 상태까지 알아도 되는지" 경계가 흐려지기 쉬웠어요.

> **해결**: 코드를 `app`(라우팅 전용) · `features`(홈·성경·큐레이션·오디오·탐색·제작 등 도메인별 모듈) · `shared`(공유 레이어) 셋으로 나누고, `shared`는 다시 `core`(api·store·타입·상수) · `lib`(범용 유틸·훅) · `components`(모든 UI 컴포넌트) · `reader`(앱 진입점) 4개로 세분화했어요. 의존 방향은 `features → shared`만 허용하고 반대 방향은 금지하는 단방향 규칙을 뒀는데, `shared/reader`(`ContentRouter`)만 유일한 예외로 features를 참조할 수 있게 열어뒀어요 — 여러 기능 화면을 한 화면에서 오케스트레이션하려면 각 기능을 알아야 하니까요. 그 외 shared 컴포넌트가 기능별 상태가 필요할 땐 규칙을 어기는 대신 props/render prop으로 주입받게 했어요(예: `CardScroller`는 페이지 인덱스나 페이지 변경 콜백을 자기 상태로 갖지 않고 prop으로만 받아요).

> **결과**: "예외 없이 지켜야 할 규칙 하나 + 명시된 예외 하나"로 단순해져서, 새 기능을 추가해도 다른 기능이나 공유 컴포넌트 코드를 건드릴 일이 없어요.

</details>

<details>
<summary><h4>노래 하나 재생했을 뿐인데 화면 4개가 같이 흔들렸다면?</h4></summary>

> **문제**: 오디오(찬양 배경음악) 재생 상태가 바뀔 때마다 관련 없는 화면까지 같이 리렌더됐어요. 원인은 구독 위치였어요 — `ContentRouter`는 홈·릴스·평독·주제별 4개 뷰를 항상 동시에 마운트해두고 화면만 슬라이드시키는 구조인데(바로 위 캐러셀 방식), 이 최상위 오케스트레이터가 `useAudioStore`에서 값 6개를 직접 구독하고 있었어요. 그래서 재생 중 오디오 상태가 바뀔 때마다 `ContentRouter` 자신은 물론 그 아래 항상 마운트돼 있는 4개 뷰까지 리렌더가 전부 전파됐어요. 여기에 `SettingsPanel`도 실제로는 안 쓰는 `useSearchParams`/`usePathname` URL 훅을 구독하고 있어서, 챕터를 이동할 때마다 불필요한 리렌더가 하나 더 겹쳤어요.

> **해결**: 오디오 상태 구독을 실제로 그 값을 쓰는 `ReaderPanels`(오디오 컨트롤 UI가 있는 곳)로 옮기고, `ContentRouter`는 콜백을 prop으로 넘겨주는 역할만 남겼어요. `SettingsPanel`에 남아있던 URL 훅도 걷어내고 필요한 값은 props로 받게 바꿨어요. "이 상태를 누가 실제로 쓰는가"를 기준으로 구독 위치만 옮긴 거지만, 상위 컴포넌트가 뷰 4개를 늘 띄워두는 구조라 상위에서 구독하면 그 대가가 뷰 1개가 아니라 4개로 곱해진다는 게 핵심이었어요.

> **결과**: 오디오 재생 중 `ContentRouter`와 나머지 3개 뷰의 불필요한 리렌더 제거, 챕터 이동 시 리렌더 27.6ms 감소.

</details>

**왜 만들었나**: 기존 React DevTools는 목록 형태라 전체 구조가 한눈에 안 들어오고, 다른 시각화 도구들은 실제 화면 구조 대신 파일 import 관계만 보여줘서 실제와 다르게 그려져요. "지금 실제로 화면에 그려지고 있는 구조"를 그대로 보여주는 도구가 없다는 걸 발견하고 직접 만들었어요.

**핵심 경험**: 리서치·설계·구현 전 과정을 75개의 의사결정 기록(ADR)으로 남기며 진행했고, npm에 실제로 배포해 누구나 설치할 수 있는 오픈소스 라이브러리로 완성했어요. 유닛 테스트 346개, 실제 오픈소스 앱 3개(excalidraw 등)로 성능 검증까지 마쳤어요.

<summary><h4>비슷한 도구가 이미 여러 개 있었는데, 전부 죽어있었어요</h4></summary>

> **문제**: "실시간 렌더 트리를 캔버스형 박스 다이어그램으로 보여준다"는 아이디어 자체는 이미 여러 팀이 시도한 적이 있었어요. 코드를 짜기 전에 React-Sight, Realize, Reactron, ReactMonitor, HiFiber 등 최소 8~9개의 선행 프로젝트부터 조사했는데, 전부 유지보수가 끊겨 있었어요. 이게 "이 문제 자체가 안 되는 문제"라는 신호인지, 아니면 다른 이유가 있는 건지부터 가려내야 했어요.

> **해결**: 죽은 프로젝트들을 하나하나 분류해보니 원인이 두 갈래로 갈렸어요. 대부분(Realize, Reactron, ReactMonitor, HiFiber)은 부트캠프 코호트의 "취업 포트폴리오용 스프린트" 프로젝트라서, 완성 직후(정확히는 코호트 종료 시점과 맞물려) 유지할 동기 자체가 사라져 죽어있었어요. 반대로 지금까지 살아있는 비슷한 도구들은 이유가 뚜렷했어요 — Reactotron은 회사가 자기 클라이언트 프로젝트에 매일 쓰는 사내 도구라서, React Scan은 커뮤니티 채택이 임계점을 넘어서서 살아있었어요.

> 딱 하나, 부트캠프 출신이 아닌데도 죽은 React-Sight는 결이 달랐어요. devtools 패널이 닫혀 있어도 계측 로직이 전역으로 계속 실행돼 프로덕션 사이트를 멈추게 하는 설계 결함이 있었고, 결국 Chrome 웹스토어가 "안전하지 않음"으로 강제 비활성화하면서 끝났어요. 동기 부족이 아니라 순수하게 기술적 설계 결함으로 죽은 유일한 사례였어요.

> 이 조사에서 나온 두 교훈을 그대로 반영했어요. React-Sight의 실패는 "관찰 도구는 절대 대상 앱을 죽이면 안 된다"는 불변 규칙으로 바로 아키텍처 문서에 못박았고, 방향 자체는 지도형(Obsidian Graph)·노드 에디터형(Figma류)·파일트리 하이브리드(CodeSee) 세 철학을 직접 비교해서, 익숙한 자유 배치 감각(노드 에디터)을 기본 골격으로 삼고 그 위에 지도형의 줌 동작만 얹는 조합으로 정했어요.

> **결과**: 코드를 한 줄도 짜기 전에 "박스+캔버스+실시간"이라는 아직 비어있는 자리를 확인하고, 선행 실패 원인(동기 부족 vs 설계 결함)을 구조적으로 갈라내 그중 기술적 교훈만 골라 초기 설계에 반영한 뒤 시작했어요.

</details>

<details>
<summary><h4>다른 개발자 도구랑 같이 켜놨다가 페이지를 통째로 멈춘 적이 있어요</h4></summary>

> **문제**: React DevTools 확장이나 react-scan처럼 이미 훅을 쓰고 있는 다른 분석 도구와 함께 켜도 서로 방해하지 않게 만들려고 했는데, 실제로 두 번 다른 방식으로 문제가 터졌어요. 먼저 `onCommitFiberRoot`를 여러 리스너가 동시에 걸릴 수 있는 getter/setter 구조로 바꿔서 react-scan과 완전히 공존시키려 했는데, 실사용 중 무한 재귀로 페이지가 완전히 멈추는 사고가 났어요. 원인은 "현재 dispatch 함수를 캡처해서 감싸 재대입"하는 흔한 패턴을 쓰면, 그 래퍼 자신이 리스너 목록에 다시 등록돼서 dispatch가 자기 자신을 다시 부르는 무한 루프가 만들어진다는 거였어요.

> 이후 실사용자가 직접 원인까지 규명해서 제보한 두 번째 문제도 있었어요. 브라우저 확장(React DevTools/Scan)은 `document_start` 시점에 페이지의 `<head>` 스크립트보다도 먼저 자기 훅을 심어버려서, "훅이 없을 때만 우리 훅을 설치한다"는 조건이 항상 거짓이 됐어요. 그 결과 Next.js처럼 하이드레이션이 런타임 부팅보다 먼저 끝나는 환경에서는 커밋을 하나도 못 잡고 노드가 영구히 0개로 보이는 문제가 있었어요.

> **해결**: 무한 재귀 사고가 난 직후엔 즉시 되돌렸어요 — 실사용 프로젝트에 건 핫픽스와 라이브러리 소스 코드 수정을 같은 시점에 짝지어야 한다는 교훈도 남겼고요(따로 고치다 소스 쪽 위험한 코드를 놓칠 뻔했거든요). 다중 리스너라는 욕심을 버리고 안전한 단일 슬롯 구조로 돌아갔어요.

> 두 번째 문제는 기존 훅이 있어도 무시하지 않고, `onCommitFiberRoot`를 "원본을 보존한 채 딱 한 번만 재할당"하는 방식으로 고쳤어요. 중복 방지 플래그를 두고, 우리 로직이 끝나면 원본 핸들러를 그대로 이어 호출해서 확장의 기능도 그대로 살아있게 했어요. 첫 번째 사고와 다른 점은, 여러 리스너를 관리하는 getter/setter 구조가 아니라 함수 프로퍼티 하나를 안전하게 딱 한 번 감싸는 것뿐이라 애초에 재귀할 여지가 없다는 거예요. 검증은 Playwright로 "확장이 먼저 훅을 심어놓은 상황"을 흉내 내서(가짜 훅을 `document_start`에 미리 주입), 보드가 정상적으로 노드를 그리고 원본 훅도 그대로 체이닝되는지까지 자동화 테스트로 확인했어요.

> **결과**: 다른 devtools 도구와 안전하게 공존(단, react-scan과의 완전한 양방향 공존은 무한 재귀 위험 때문에 의도적으로 보류), 확장 선점 케이스를 포함한 자동화 검증 통과.

</details>

<details>
<summary><h4>4가지 빌드 도구를 전부 자동으로 지원했어요</h4></summary>

> **문제**: "설치 한 줄이면 앱 소스 코드는 한 글자도 안 건드리고 계측 스크립트가 자동으로 붙는다"는 목표를 세웠는데, 이게 Vite·webpack·Rspack·Next.js(Turbopack) 4개 빌드 도구 전부에서 실제로 가능한지는 아무도 검증한 적이 없었어요. 모든 dev 서버가 HMR을 위해 "서빙되는 HTML에 스크립트를 끼워 넣는" 기능을 갖고 있을 거라는 가설은 있었지만, 도구마다 그 기능을 여는 문(공식 API)이 다르고 실제로 열리는지는 직접 최소 프로젝트를 만들어봐야 알 수 있었죠.

> **해결(가능성 검증)**: 4개 도구 각각에 최소 스파이크 프로젝트를 만들어, git diff로 앱 소스가 정말 안 바뀌는지, 화면에 표시가 실제로 뜨는지, React의 내부 훅이 실제로 호출되는지까지 Playwright로 실측했어요. Vite와 webpack은 각자 공식적으로 이 용도로 제공하는 API가 그대로 먹혔지만, Rspack은 API 자체는 호환됐는데도 스캐폴드 기본 설정(모듈 시스템 충돌, 기본 내장 플러그인이 따로 있다는 점) 때문에 두 번이나 막혔어요 — "플러그인 API가 호환된다"와 "기본 프로젝트 설정이 호환된다"는 서로 다른 질문이라는 걸 이때 배웠죠. 가장 뜻밖이었던 건 Next.js(Turbopack)였어요. Next.js가 공식적으로 안내하는, "하이드레이션 전에 실행된다"는 전용 파일 방식을 써봤는데 계속 실패했고, 원인을 추적해보니 Next.js 자신의 개발 모드 런타임이 우리보다 2.5밀리초 먼저 같은 전역 훅 자리를 선점해버리고 있었어요. 오히려 훨씬 오래된 방식(최상단 레이아웃 파일의 `<head>`에 동기 스크립트를 직접 넣는 방식)이 문서가 파싱되는 순서상 더 일찍 실행돼서 성공했고요.

> **해결(테스트 자동화)**: 실제 설치 자동화 CLI를 구현한 뒤에도, 실사용 중 발견된 중대한 버그들(Turbopack 이름 압축, DevTools root 오염, webpack CSS 미적용 등)이 하필 전부 "특정 빌드 도구 조합에서만" 재현되는 걸 겪었어요. 그래서 한 번 손으로 확인하고 끝내는 대신, 네 경로 각각에 대해 실제로 패키지를 설치하고 `init`을 돌리고 dev 서버를 띄워 화면과 콘솔을 Playwright로 검증하는 e2e 테스트를 스택별로 만들었어요. 이때 "패키지매니저×번들러×React 버전을 전부 곱하면 매트릭스가 폭발한다"는 것도 미리 판단해뒀는데, 실제로 코드 경로 자체가 갈리는 축은 주입 지점이 다른 번들러뿐이고 패키지매니저나 React 버전 차이는 그 위에서 드물게 터지는 예외 케이스일 뿐이었어요. 그래서 매트릭스를 곱하지 않고 축을 분해해서 번들러 4개만 깊게 자동 검증하고, 나머지는 문제가 실제로 보고될 때만 얕게 대응하기로 정했고요. 이 4개 테스트를 한 번에 실행하는 오케스트레이터를 만들어 `npm publish` 직전에 자동으로 돌도록 걸어뒀어요 — 배포 전에 사람이 수동으로 돌리는 걸 깜빡할 수 있다는 우려가 있었기 때문에, "잊지 않고 돌리겠다"가 아니라 배포라는 이벤트 자체에 검증을 묶어버린 거예요.

> **결과**: 4개 빌드 도구 전부에서 앱 소스 코드를 단 한 줄도 건드리지 않고 자동 주입이 기술적으로 가능하다는 걸 증명한 데서 그치지 않고, 그 네 경로 전부를 실제로 띄워 검증하는 테스트 자동화까지 만들어 배포 게이트에 걸었어요. 그 뒤로는 어떤 경로 하나라도 깨진 채로는 `npm publish` 자체가 실패하도록 만들어서, 네 가지 빌드 도구 지원이 "한 번 확인하고 끝"이 아니라 배포마다 계속 보장되는 상태가 됐어요.

</details>

<summary><h4>느려지는 원인을 직접 찾아 최대 28배 빠르게 개선했어요</h4></summary>

> **문제**: 컴포넌트가 5,000개 규모로 늘어나면, 클릭 반응 속도가 작은 트리 대비 최대 28배까지 느려졌어요. 이미 "화면 밖 요소는 실제 DOM 렌더를 건너뛴다"는 최적화가 있었는데도 이 정도였다는 게 이상했죠. 그래서 추측 대신, 렌더 파이프라인 각 단계에 성능 측정 코드를 심어 어디가 시간을 먹는지부터 실측했어요.

> **진단**: 데이터를 화면 좌표로 바꾸고 배치를 계산하는 단계는 5,000개 규모에서도 몇 밀리초라 문제가 아니었어요. 진짜 비용은 "실제로 화면에 그려지기까지"의 구간에 있었는데, 그 안에서 캔버스 라이브러리가 노드마다 만드는 내부 래퍼 컴포넌트가 클릭 몇 번에 1만 5천 번 가까이 다시 실행되고 있었어요. 정작 화면에 그려진 노드는 그중 200여 개뿐이었는데도요. 즉 기존 최적화는 눈에 보이는 결과물(DOM)만 건너뛸 뿐, 그 전에 라이브러리가 배열 전체를 훑는 내부 비용은 전혀 줄여주지 못했던 거예요. 이 비용은 "몇 개가 보이는가"가 아니라 "배열에 원소가 몇 개 들어있는가"에 비례했어요.

> **해결**: 화면에 실제로 걸치는 영역(약간의 여유 마진 포함)에 속한 그룹만 개별 컴포넌트와 연결선을 만들어 배열에 담고, 화면 밖 그룹은 아예 배열에 넣지 않고 이름표 하나짜리 틀만 남겼어요. 드래그 중 매 프레임 이 계산을 다시 하면 최적화 자체가 무의미해지니, 마지막 움직임 이후 화면이 안정된 뒤에만 반영되도록 했고요.

> **결과**: 28배까지 벌어지던 응답 속도가 노드 수와 거의 무관하게 1배 안팎으로 평탄해졌고, 실제 대형 오픈소스 프로젝트(약 9,800개 노드)에서도 비슷한 개선폭을 확인했어요. 뜻밖의 수확도 있었는데, 별개로 알려져 있던 "초당 렌더 빈도가 높을 때 느려지는" 문제도 같은 수정으로 함께 해소됐어요. "노드 개수"와 "갱신 빈도"는 서로 다른 스트레스 상황이었지만, 근본 병목이 같았기 때문이었어요.

</details>

<details>
<summary><h4>배포된 버전에서 한 번도 작동한 적 없던 기능을 발견해서 고쳤어요</h4></summary>

> **문제**: 실사용자가 지적했어요. 보드 노드를 더블클릭하면 실제 화면 요소를 하이라이트해주는 기능도, Alt+클릭으로 실제 요소에서 보드 노드로 거꾸로 이동하는 기능도 전혀 동작하지 않는다고요. "기능 절반이 안 되는데 왜 된다고 했냐"는 정당한 지적이었어요.

> **원인**: 이 두 기능의 코드에는 "개발 모드에서만 실행"하는 조건문이 들어 있었는데, 그 조건을 판별하는 방식이 빌드 도구가 배포용으로 빌드할 때 값을 미리 고정해버리는 방식이었어요. 배포용 빌드는 항상 "개발 모드 아님"으로 고정되니, 그 조건문 아래 실제 로직 전체가 "절대 실행될 수 없는 코드"로 간주돼 빌드 과정에서 통째로 삭제되고 있었던 거예요. 실제로 배포된 결과물을 열어보니 두 기능의 핵심 로직이 흔적도 없이 사라져 있었고요. 이건 이번에 새로 생긴 버그가 아니라, 이 기능들이 처음 만들어진 이후 배포된 모든 버전에 처음부터 있던 결함이었어요 — 설치한 사람 중 누구도 이 두 기능을 정상적으로 써본 적이 없었던 거죠. 비슷한 다른 코드(주입 진입점)는 이미 예전에 같은 문제를 피해가는 방식으로 고쳐져 있었는데, 정작 이 두 파일은 그 수정에서 빠져 있었어요.

> **해결**: "개발 모드인지"를 판별하는 방식을 하나로 통일했어요. 빌드 도구가 미리 값을 고정해버리는 판별 방식 대신, 브라우저에서 실제로 실행되는 순간에만 값을 알 수 있는 전역 신호(주입 레이어가 개발 서버에서만 심어두는 값)를 우선 확인하도록 바꿔서, 빌드 도구가 아무리 배포용으로 빌드해도 이 조건이 미리 고정될 수 없게 만들었어요. 그리고 이 판별 로직을 쓰는 모든 파일이 각자 따로 구현하지 않고 공용 함수 하나만 쓰도록 통일했어요.

> **결과**: 배포된 결과물을 다시 열어 실제 로직이 온전히 살아있는 걸 확인했고, 실사용 프로젝트에 반영해 더블클릭·Alt+클릭 두 기능이 정상 동작하는 것도 실측으로 확인했어요. "개발 전용 코드"라는 같은 패턴이 파일마다 따로 구현돼 있으면, 한 곳만 고치고 나머지를 놓치기 쉽다는 것도 이번에 직접 겪은 뒤로 프로젝트 전체를 훑어 통일하는 계기가 됐어요.

</details>

<summary><h4>이 도구는 사실 코드를 한 줄도 안 읽어요</h4></summary>

> **문제**: 화면에 지금 실제로 그려지고 있는 컴포넌트 구조를 얻으려면, React가 공식적으로 공개하지 않은 내부 통로(devtools 훅)를 건드려야 해요. 선행 조사(바로 위 하이라이트)에서 이미 확인했듯, 이 부분을 직접 구현하는 건 선행 프로젝트들이 죽은 지점이었어요 — React 버전이 바뀔 때마다 내부 구조가 달라져서 계속 깨졌거든요.

> **해결**: 그래서 이 도구는 소스 코드를 파싱하지 않아요. 대신 React가 dev 모드에서 스스로 심어두는 `window.__REACT_DEVTOOLS_GLOBAL_HOOK__`(React DevTools를 위한 공식 통로)의 `onCommitFiberRoot`를 가로채서, 커밋될 때마다 "지금 실행 중인" Fiber 트리를 읽어요. 이 트리를 `RenderNode`라는 정규화된 스키마로 직렬화해 구독 가능한 store에 스냅샷으로 쌓고, React Flow 캔버스가 그 store를 구독해서 박스+선 다이어그램으로 그려요. 전 과정이 dev 전용이라 프로덕션에는 아예 끼어들지 않아요.

> 훅킹 레이어 자체는 직접 만들지 않고 위임했어요(bippy). 실제로 원조 React-Sight의 로드맵 마지막 항목도 "직접 재구현하지 말고 devtools 백엔드에 훅킹하기"였는데, 이 프로젝트는 그 교훈을 처음부터 실행한 셈이에요. 다만 라이브러리를 그대로 믿지도 않았어요 — bippy의 README에 적힌 함수가 실제 설치된 버전엔 없거나 이름이 다른 경우를 두 번 발견한 뒤로는, "새 버전을 올리거나 새 유틸을 쓸 땐 문서 말고 실제 설치된 패키지의 소스를 직접 확인한다"는 규칙을 프로젝트에 못박았어요.

> **결과**: React 버전이 바뀌어도 훅킹 로직 자체가 깨질 리스크를 크게 줄였고, 소스 코드 분석 없이 런타임 관찰만으로 실제 렌더 구조를 정확히 얻어요.

</details>

<details>
<summary><h4>컴포넌트 이름이 전부 알 수 없는 문자로 보였는데, 범인은 Next.js 자신이었어요</h4></summary>

> **문제**: 실사용 중인 Next.js(Turbopack) 프로젝트에서 보드에 뜨는 컴포넌트 이름이 전부 "ui", "ew", "c8", "eS" 같은 알아볼 수 없는 문자였어요. 게다가 페이지 쪽 요소를 Alt+hover로 짚으면 보드에서 반응했지만, 반대로 보드 노드를 클릭해 실제 요소로 이동하는 건 항상 실패했어요. 같은 패키지를 쓰는 Vite·webpack 프로젝트에서는 이런 문제가 전혀 없었죠.

> **해결**: 처음엔 Turbopack이 이름을 압축(망글링)하는 줄 알았는데, 실제로 재현 스파이크를 만들어 확인해보니 압축된 이름의 함수 소스 안에 `enableCacheIndicator`, `shadowRoot` 같은 문자열이 들어 있었어요 — 이건 대상 앱의 코드가 아니라 **Next.js가 자체적으로 그리는 DevTools 오버레이 UI**(FPS 인디케이터 등)였어요. 보드의 데이터 저장소가 "가장 최근에 커밋된 root 하나만 남기는" 방식으로 동작하는데, Next의 오버레이가 계속 자체 커밋을 발생시키다 보니 항상 마지막 커미터가 되어 대상 앱 대신 이 오버레이 트리를 그리고 있었던 거예요. 역방향 이동이 안 됐던 것도 같은 이유였고요 — 실제 앱의 fiber id를 돌려받아도 보드가 들고 있는 트리(오버레이 트리)엔 그 id가 없으니 이동할 곳이 없었던 거죠. 커스텀 엘리먼트·Shadow DOM 여부 같은 실측 패턴으로 이런 "도구 오버레이 root"를 판별해 관찰 대상에서 제외하도록 고쳤어요.

> **결과**: 이름 문제가 아니라 "엉뚱한 트리를 보여주고 있었다"는 진짜 원인을 찾아내 대상 앱의 실제 컴포넌트 트리와 이름이 정상적으로 표시됐고, 노드 클릭 → 실제 요소 이동도 함께 복구됐어요.

</details>

<details>
<summary><h4>77개 컴포넌트가 전부 "확인 중"에서 멈췄는데, 에러 로그는 0건이었어요</h4></summary>

> **문제**: 실사용 리포트로, 어떤 Next.js(Turbopack) 프로젝트에서 보드를 열면 렌더 트리 캡처 자체는 정확했어요(구조·이름 전부 실제 앱과 일치, 콘솔 에러도 0건). 그런데 컴포넌트 77개 전부가 "(그룹 확인 중…)" 상태에 갇힌 채 몇 초, 몇십 초가 지나도 풀리지 않았어요. 제보자는 "Turbopack에서 특정 파싱이 안 되는 것 같다"고 추정했죠.

> **해결**: 컴포넌트가 속한 그룹을 알아내는 로직은 여러 컴포넌트를 하나의 배치로 묶어 한 번에 처리하는데, 그 배치 전체가 "모두 끝나야 완료"로 짜여 있었어요. 그런데 그중 하나라도 내부적으로 쓰는 sourcemap 조회가 (에러 없이) 응답만 영원히 안 오는 상태로 멈춰버리면, 그 하나 때문에 배치 전체가 영원히 안 끝났어요 — 에러가 안 나는 이유도 바로 이거였고요(실패한 게 아니라 그냥 멈춘 거라 catch할 대상 자체가 없었거든요). 초기 화면처럼 컴포넌트 대부분이 같은 배치에 몰리는 상황이면, 정확히 리포트대로 전부가 함께 갇혀요. 즉 원인은 Turbopack의 파싱 실패가 아니라, 애초에 "멈춤"에 대비한 타임아웃 처리가 어디에도 없었다는 설계 공백이었어요. 개별 조회마다 타임아웃을 걸어, 시간 안에 안 끝나면 그 컴포넌트만 기존에 있던 대체 방식(파일 기준 그룹핑)으로 넘기고 나머지 배치는 그대로 진행하도록 고쳤어요.

> **결과**: 어떤 번들러에서 어떤 조회가 무응답으로 멈추더라도 보드 전체가 영구히 멎지 않고, 정해진 시간 후 자동으로 대체 경로를 타 정상 동작해요. 제보자가 별도 이슈로 등록하려던 것도 번들러 문제가 아니라 저희 쪽 멈춤 처리 부재였다는 걸 먼저 밝혀 불필요한 이슈 등록을 막았어요.

<summary><h4>노드가 많을수록 더 심하게 망가지는 줄 알았는데, 아니었어요</h4></summary>

> **문제**: 실사용 앱에서 컴포넌트가 많은 화면일수록 그룹이 뭉개지는 현상이 있었어요. 컴포넌트 1,716개짜리 화면은 288개짜리 화면보다 훨씬 심하게 그룹 1~3개로 뭉쳐버렸죠. 자연스럽게 "노드(컴포넌트) 개수가 많아질수록 처리가 못 따라가서 생기는 문제"라고 의심했어요.

> **해결**: 직접 컴포넌트 개수를 11,000개 넘게까지 늘려 테스트해봤는데, 오히려 타임아웃도 실패도 0건이고 그룹도 안정적이었어요 — "개수가 많아서"라는 가설이 실측으로 깨진 거예요. 다시 원인을 파고들어 보니, 진짜 원인은 개수가 아니라 "서로 다른 소스 파일이 몇 개인지"와 "그 파일들을 읽어오는 타이밍이 겹치는지"였어요. 한 화면의 컴포넌트들을 한꺼번에 묶어 처리하는데, 이 파일 조회 작업들에 개별로 걸어둔 제한 시간이 전부 같은 시점에 동시로 시작되고 있었거든요. 그러다 보니 화면 진입 직후처럼 조회할 파일이 많고 마침 다른 요청들과 겹치는 순간엔, 뒤에 줄 선 조회들이 실제로는 아직 시작도 못 했는데 "제 순서를 기다리다가" 시간을 다 써버려 억울하게 실패 처리됐어요. 게다가 한 번 그렇게 실패로 기록되면 이후에도 다시 시도하지 않도록 짜여 있어서, 일시적인 병목이 그 화면 내내 고정되는 문제로 굳어졌죠. 이걸 고치기 위해 동시에 진행되는 조회 개수에 상한을 둬서 제한 시간이 "대기 시간"이 아니라 "진짜 조회 시간"만 재도록 바꿨고, 일시적으로 실패한 항목은 완전히 포기하지 않고 다음 기회에 몇 번 더 재시도하도록 구분했어요.

> **결과**: 대형 화면에서도 억울한 실패 비율이 크게 줄었고, 일시적으로 실패한 항목도 이후 기회에 회복돼 그룹이 소수로 뭉개지던 문제가 풀렸어요. 무엇보다 "개수가 원인"이라는 그럴듯한 첫 가설을 직접 실측으로 반증하고 나서야 진짜 원인(타이밍 경합)을 찾아낼 수 있었어요.

<summary><h4>로컬에서는 멀쩡한데 배포하면 화면이 텅 비었어요</h4></summary>

> **문제**: 배포용 데모 게이트(개발 모드에서만 계측이 켜지도록 하는 플래그)를 고쳤는데도, 실제 배포 사이트를 열면 보드가 "커밋 0회 · 노드 0개"로 계속 텅 비어 있었어요. 콘솔에는 계측이 시작됐다는 로그까지 정상적으로 찍혔는데도요. 로컬에서 똑같은 빌드를 돌리면 이 문제가 재현되지 않았어요.

> **해결**: 게이트 자체는 문제가 아니라는 걸 먼저 확인한 뒤, 배포용 코드가 브라우저에서 실제로 어떤 순서로 실행되는지를 직접 추적 로그로 심어 확인했어요. 그 결과, React 라이브러리 코드가 먼저 평가되고 나서야 이 도구의 훅 설치 코드가 뒤늦게 실행되고 있다는 걸 발견했어요. React는 딱 한 번, 자기 코드가 평가되는 순간에만 "감시 도구가 있는지" 확인하고 없으면 그 뒤로 다시는 확인하지 않는데, 배포용 번들에서는 하필 이 순서가 뒤바뀌어 있었던 거예요. 로컬 개발 서버는 우연히 코드가 실행되는 순서가 달라서 이 문제 자체가 드러나지 않았을 뿐이었죠. 그래서 이 도구의 훅 설치 코드를, React 관련 코드보다 무조건 먼저 실행되도록 배포 진입점의 맨 앞으로 옮겼어요.

> **결과**: "감시 도구가 켜졌는지" 확인용 로그가 정상인데 데이터가 0건이라면, 게이트 문제보다 먼저 "설치 코드와 React 코드 중 뭐가 더 먼저 실행되는지"부터 의심해야 한다는 걸 배웠어요 — 로컬에서는 되는데 배포에서만 안 된다면 특히요.

<summary><h4>예쁘게 그리는 것보다 먼저 정한 원칙이 있었어요</h4></summary>

> **문제**: 컴포넌트 수백~수천 개짜리 트리를 화면 하나에 그려야 하는데, 사람이 실제로 이해할 수 있는 그래프 시각화 방식이 뭔지부터 정하지 않으면 알고리즘부터 손대는 게 의미가 없었어요. "여러 노드를 하나로 뭉쳐서 단순해 보이게" 만드는 방식(super-noding)이 흔한 접근이지만, 관련 연구를 찾아보니 대부분의 사람은 이런 방식을 오히려 잘 못 읽어낸다는 결과가 있었어요.

> **해결**: 그래서 "처음부터 다 단순화하면 정보가 사라지고, 처음부터 다 보여주면 스파게티가 된다"는 문제를, 컴포넌트를 뭉쳐서 숨기는 대신 지역(회색 경계 박스)으로만 나누고 실제 노드는 전부 그대로 보여주는 지도형(map-like) 방식으로 풀기로 먼저 정했어요. 줌 아웃하면 영역 이름만, 줌 인하면 실제 컴포넌트가 드러나는 점진적 공개(progressive disclosure) 원칙도 이때 확정했고요. 이후에 검토한 노드 에디터(자유 배치 박스+선) 골격, 검색 기능, 그리고 아래 트리 배치·엣지 라우팅 알고리즘들은 전부 이 원칙 — "뭉치지 않고 영역으로 나눈다" — 을 구현하기 위한 수단이었어요. 대신 색상이나 인터랙션처럼 되돌리기 쉬운 부분과, 트리 데이터 스키마처럼 이후 시각화 코드 전체가 의존해 되돌리기 어려운 부분을 미리 구분해뒀어요.

> **결과**: "예쁘게 그리는 법"이 아니라 "무엇을 숨기고 무엇을 항상 보여줄지"를 먼저 정해뒀기 때문에, 이후 알고리즘을 여러 번 갈아엎으면서도(아래 하이라이트들) 시각화의 기본 방향 자체는 한 번도 흔들리지 않았어요.

</details>

<summary><h4>트리 배치, 지적 한 번에 알고리즘을 통째로 갈아엎었어요</h4></summary>

> **문제**: 처음엔 그룹을 각 깊이(층)별로 왼쪽부터 등장 순서대로 채우는 단순한 배치를 썼어요. 그런데 실제로 그려보니 같은 깊이인데도 폭이 넘쳐 줄이 나뉘어 계층이 다른 것처럼 오해되고, 자식 그룹이 부모 바로 아래가 아니라 엉뚱한 위치에 놓여 부모-자식 선이 화면을 길게 가로지르는 문제가 있었어요.

> **해결**: 먼저 자식 그룹들을 부모의 중심 x좌표 쪽으로 끌어당겨 겹치지 않게 배치하는 방식(부모 앵커 배치)으로 고쳤어요. 그런데 이 방식은 겹치는 자식을 항상 오른쪽으로만 밀어내다 보니, 부모가 자식 무리의 왼쪽 끝에 걸리고 자식이 많을수록 전체가 오른쪽으로 점점 치우치는 부작용이 있었어요. "자식이 우측으로 치우치는데 이게 직관적인가, 중앙으로 모으는 게 낫지 않나"라는 지적을 받고서야 진짜 문제가 "배치 순서"가 아니라 "부모가 자식 중앙이 아니라 왼쪽 끝에 있는 것"이라는 걸 깨달았어요. 그래서 좌우 순서(소스 코드에 자식을 쓴 순서 그대로라 이미 직관적이었어요)는 그대로 두고, 자식들을 먼저 배치한 뒤 부모를 그 자식들이 차지하는 폭의 정중앙 위에 놓는 트리 배치 알고리즘(tidy-tree)으로 통째로 교체했어요. 여러 부모를 공유하는 컴포넌트는 트리로 못 다루니, 등장 순서가 가장 앞선 부모 하나를 대표로 골라 그 아래 중앙 정렬하고 나머지 부모와의 연결은 선으로만 남겼고요.

> **결과**: 부모가 자식 스팬의 정중앙(오차 1픽셀 수준)에 오는 대칭적인 트리 구조로 바뀌어, 큰 트리에서도 "누가 누구를 렌더하는지"가 한눈에 읽혀요. 한 번의 배치 방식으로 끝내지 않고, 사용자 피드백을 계기로 실측 기반 대안 비교를 거쳐 더 정석에 가까운 알고리즘으로 다시 갈아엎은 경험이었어요.

</details>

<summary><h4>선이 다 똑같아 보였던 이유, 보고 있던 지점이 틀렸어요</h4></summary>

> **문제**: 선의 색으로 "어느 그룹에서 출발했는지"를 구분하도록 설계해뒀는데, 한 그룹이 여러 컴포넌트를 동시에 렌더하는 화면(허브 구조)에서는 선 9개가 전부 같은 색으로 뭉쳐 보였어요. "선들이 비슷하게 뭉쳐서 구별이 거의 안 된다"는 피드백을 받았고, 처음엔 선이 지나가는 경로가 겹쳐서 그런 줄 알았어요.

> **해결**: 실제로 뜯어보니 겹침 문제가 아니었어요. 9개 선 모두 같은 그룹에서 출발했으니, "출발지 기준 색칠"이라는 규칙 아래에서는 애초에 다 같은 색이 나오는 게 당연했던 거예요 — 즉 출발지라는 정보 자체가 이 상황에선 아무것도 구별해주지 못했던 거죠. 진짜 구별할 수 있는 정보는 "어디서 왔는지"가 아니라 "어디로 가는지"(도착지)였어요. 그래서 각 선을 출발지 색에서 도착지 색으로 이어지는 그라데이션으로 바꿔, 한 곳에서 나온 선이라도 각자 다른 도착지 색으로 끝나며 자연스럽게 구별되도록 했어요. 또 선을 점선으로 그리던 규칙이 이 그라데이션의 색 흐름을 조각내 오히려 안 읽히게 만든다는 것도 확인해서, 그 경우엔 실선으로 바꿨어요.

> **결과**: 같은 곳에서 뻗어나가는 선들도 끝 색깔로 목적지가 구분돼, 복잡한 허브 구조에서도 "이 선이 어디로 가는지"를 한눈에 좇을 수 있게 됐어요. 겹침이라는 눈에 보이는 증상 대신, 애초에 어떤 정보를 색으로 인코딩하고 있었는지부터 다시 짚어봐야 했던 문제였어요.

</details>

<details>
<summary><h4>여기저기 쓰이는 컴포넌트 하나가 트리 전체를 꼬아놨어요</h4></summary>

> **문제**: 트리를 부모 중심 정렬로 예쁘게 그리는 알고리즘(바로 위 하이라이트)을 만들어놓고도, 특정 상황에서 배치가 그릴 때마다 미묘하게 흔들리고 불필요하게 긴 선이 생기는 경우가 있었어요. 실제 React 렌더 트리는 컴포넌트 인스턴스 단위로는 항상 부모가 하나뿐인 순수한 트리인데, 이상하게도 배치 알고리즘 입장에서는 부모가 둘 이상인 것처럼 보이는 경우가 있었죠.

> **해결**: 원인을 추적해보니, 같은 파일(같은 타입)을 하나의 그룹으로 묶어 표시하는 방식 때문이었어요. 예를 들어 `Dialog` 같은 공용 컴포넌트가 서로 다른 화면 두 곳에서 각각 쓰이면, 그 두 사용처가 서로 다른 부모인데도 "Dialog 그룹"이라는 하나의 그룹으로 합쳐지면서 그 그룹이 부모를 두 개 갖게 된 거예요. 이 다중 부모 상태가 트리 배치 알고리즘의 전제(부모는 하나)를 깨서, 그 그룹을 어느 부모 아래 대표로 놓을지가 매번 미묘하게 바뀌며 전체가 흔들렸던 거고요. 그래서 부모가 둘 이상인 그룹은 아예 메인 트리에서 빼서, 화면 아래쪽에 별도의 "공유 UI 레인"으로 옮겼어요. 각 사용처에는 "이 컴포넌트를 여기서도 쓴다"는 작은 표식만 남기고, 실제 연결선은 평소엔 안 그리다가 마우스를 올렸을 때만 보여주는 방식으로 바꿨죠.

> **결과**: 메인 트리에서 다중 부모 문제가 완전히 사라져 모든 노드가 부모 하나뿐인 순수한 트리가 됐고, 그릴 때마다 흔들리던 배치가 안정됐어요. 화면을 가로지르던 긴 선도, 평소엔 숨겨두고 필요할 때만 보여주는 방식으로 정리됐고요.

<summary><h4>선이 겹치지 않게, 길찾기 알고리즘을 직접 짰어요</h4></summary>


https://github.com/user-attachments/assets/8de0af31-77d0-4b4e-bd31-2488176f8a92


> **문제**: 같은 그룹 안 부모-자식 선은 트리 배치 덕분에 자연스럽게 깔끔했지만, 그룹 경계를 넘나드는 선은 문제였어요. 컴포넌트 15개 정도의 단순한 데모에서는 눈에 안 띄었는데, 실제 큰 프로젝트(그룹 수십~수백 개)를 그려보니 이 경계를 넘는 선들이 다른 그룹의 박스를 그대로 뚫고 지나가는 경우가 흔했어요. 데모만 보고 "이 정도면 괜찮다"고 넘어갔다면 발견하지 못했을 문제였죠.

> **해결**: 기존 라이브러리(예: libavoid)를 그대로 가져다 쓰는 대신, 우리 화면 좌표만으로 동작하는 길찾기 알고리즘을 직접 짰어요. 선의 시작점·끝점·모든 박스의 모서리 좌표들로 격자를 만들고, 그 격자 선을 따라 박스를 피해가면서 "가장 짧고 덜 꺾이는" 경로를 A* 알고리즘으로 탐색하는 방식이에요. 처음 짠 버전은 간단한 우회 경로 몇 가지만 시도하다 안 풀리면 결국 그냥 관통하는 방식으로 물러섰는데, 격자+A* 방식으로 바꾸면서 우회로가 존재하기만 하면 반드시 찾아내도록 만들었어요. 또 선이 항상 자기 그룹 박스 밖으로 빠져나온 뒤에야 꺾이도록 하고, 같은 출발 그룹의 선들은 같은 통로를, 다른 출발 그룹의 선들은 서로 다른 통로를 쓰도록 분리해서 통로 안에서 선끼리 겹치는 것도 줄였어요.

> **결과**: 실제 규모의 프로젝트에서도 경계를 넘는 선이 다른 그룹 박스를 뚫고 지나가는 경우가 0건이 됐고, 좌표 계산이 순수 함수라 트리 구조가 안 바뀌면 매 렌더마다 다시 계산하지 않아 성능 부담도 없었어요. 작은 데모로는 안 보이던 문제를 실제 규모에서 검증하고서야 알고리즘을 직접 짜야 한다는 판단을 내릴 수 있었어요.

<summary><h4>설계 문서를 쓰다 보니 계속 거짓말이 됐어요</h4></summary>

> **문제**: 오픈소스로 전환하며 외부 기여를 받으려면 코드를 처음 보는 개발자를 위한 문서가 필요했어요. 그런데 이미 있던 설계 문서를 다시 열어보니, "훅킹 라이브러리 후보 비교 중"이나 "스키마 초안" 같은 구현 전 단계의 문장이 그대로 남아 있었어요. 실제로는 이미 오래전에 특정 라이브러리로 확정됐고 스키마도 여러 번 바뀐 뒤였는데도요. 코드가 실제로 하는 일을 문서에 다시 옮겨 적는 방식 자체가, 코드가 바뀔 때마다 문서를 계속 거짓말로 만들고 있었던 거예요.

> **해결**: 반대로, 75개나 쌓인 결정 기록(ADR) 문서들은 하나도 안 썩어 있었어요. 이유를 짚어보니, ADR은 "그 시점에 왜 이렇게 결정했는지"를 기록한 것이라 이후에 코드가 바뀌어도 그 결정을 내렸던 사실 자체는 여전히 참이기 때문이었어요. 그래서 "코드가 지금 뭘 하는지"를 다시 서술하는 문서는 애초에 안 만들기로 하고, 기존 설계 문서를 걷어내는 대신 "깨면 안 되는 규칙 몇 개 + 이 버그면 여기부터 찾아보라는 지도 + 관련 ADR로 가는 길잡이"만 담은 1~2페이지짜리 코드 맵으로 바꿨어요. 알고리즘 세부 설명이나 모듈별 API 문서는 일부러 안 만들었고요. 대신 "레이어 경계나 규칙 자체가 바뀌는 결정을 내리면 이 문서도 같은 커밋에서 함께 고친다"는 규칙 한 줄만 프로젝트 규칙에 추가했어요.

> **결과**: 코드의 세부 동작이 아니라 잘 안 바뀌는 불변 규칙만 문서화했기 때문에 갱신 부담이 크게 줄었고, 처음 오는 기여자가 코드를 전부 읽지 않고도 "이 변경이 프로젝트의 근본 규칙을 건드리는지"를 스스로 판단할 수 있게 됐어요. 문서를 쓰다가 문서가 계속 거짓이 되는 걸 겪고 나서야, "무엇을 문서화할지"보다 "무엇을 문서화하면 안 되는지"를 먼저 정해야 한다는 걸 배웠어요.

<summary><h4>공식 API가 안 주는 정보를, React 내부를 뒤져서 찾아냈어요</h4></summary>

> **문제**: 컴포넌트를 파일 단위로 묶어 보여주던 걸, 사용자가 한 단계 위인 폴더 단위(예: 같은 도메인 폴더 안 파일 여러 개를 하나로)로도 묶고 싶어 했어요. 그런데 지금 그룹핑에 쓰던 라이브러리 함수는 소스맵을 심볼리케이션하면서 파일명만 남기고 폴더 경로 정보를 깎아버렸어요 — 애초에 참조하는 소스맵 자체에 폴더 경로가 없었거든요. 공식적으로 기대할 수 있는 경로로는 이 정보를 얻을 방법이 없어 보였어요.

> **해결**: 그런데 React 19의 파이버 안에 있는, 컴포넌트가 어디서 호출됐는지 추적하는 내부 값(owner 스택)에는 전체 경로가 URL 형태로 고스란히 남아있다는 걸 발견했어요. 이건 우리 코드 저장소의 파일을 직접 읽는 게 아니라, 지금까지 해온 것과 똑같이 런타임에서 실제로 관찰되는 파이버 값을 읽는 방식이었죠. 이 값을 직접 파싱해서 폴더 경로를 복구했고, 실제 40개 컴포넌트 전부에서 성공적으로 복구되는 걸 확인했어요. 이 정보가 없는 경우(예: 프로덕션 빌드)에는 조용히 기존 파일 그룹핑으로 되돌아가도록 만들어 안전판도 남겼고요. 폴더 프레임이 파일 프레임을 감싸는 2단 중첩 구조는, 기존 배치 로직을 다시 짜지 않고 폴더 안 파일 배치와 최상위 배치에 같은 배치 함수를 재사용하는 방식으로 얹었어요.

> **결과**: 공식적으로 제공되지 않는 폴더 구조 정보를 런타임 관찰만으로 복구해, "폴더로 묶기" 토글 하나로 파일 단위와 폴더 단위 두 가지 시야를 모두 지원할 수 있게 됐어요. 이 정보를 못 얻는 환경에서도 기존 파일 그룹핑으로 조용히 폴백해, 기능이 늘어난 만큼 지원 범위가 줄지는 않았어요.

<summary><h4>만들기만 한 게 아니라, 진짜로 배포까지 해봤어요</h4></summary>

> **문제**: Vite·webpack·Next.js 세 가지 번들러 모두에서 설치부터 실행까지 되는 걸 로컬로 확인했다고 해서, 그게 실제로 남이 npm에서 설치해 쓸 수 있다는 뜻은 아니었어요. "설치 명령 한 줄이면 바로 쓸 수 있게 하고 싶다"는 목표를 로컬 검증만으로는 끝까지 확인할 수 없었죠.

> **해결**: 그래서 실제로 npm 공개 레지스트리에 배포했어요. 배포하자마자 실전에서 바로 문제가 드러났는데, 명시해둔 React 버전 조건이 실제 최신 프로젝트가 설치하는 버전보다 더 좁아서 설치 자체가 실패하는 버그가 있었어요 — 로컬 개발 환경에 우연히 깔려 있던 버전을 그대로 조건에 박아 넣은 실수였죠. 이건 실제로 배포하고 새 프로젝트에 설치해봐야만 드러나는 문제였고, 바로 다음 버전으로 고쳐 재배포했어요. 이어서 "설치 명령 한 줄로 끝나야 한다"는 목표를 완성하려고 설치 직후 자동으로 설정을 끝내는 기능도 추가했는데, 이 기능이 실행되는 위치가 사용자 프로젝트가 아니라 패키지 자신의 위치로 바뀌는 함정이 있어서, 실제 대상 경로를 다른 방식으로 알아내고 자기 자신의 저장소를 잘못 건드리지 않는 안전장치, 그리고 이 기능이 무슨 이유로든 실패해도 전체 설치 자체는 절대 실패시키지 않는 안전장치까지 함께 넣었어요. 또 다른 패키지 매니저(pnpm)에서는 보안 정책상 이런 자동 설정이 원천적으로 차단된다는 것도 실제로 설치해보고서야 알게 됐고, 이건 패키지 쪽에서 우회할 수 없는 정책이라는 걸 확인한 뒤 문서로 안내하는 방식을 택했어요.

> **결과**: 로컬 검증만으로는 못 잡았을 실전 설치 실패를 실제 배포 후 빠르게 발견해 고쳤고, npm·yarn에서는 정말로 설치 한 줄만으로 바로 쓸 수 있는 상태를 만들었어요. "만들었다"와 "남이 실제로 설치해서 쓸 수 있다" 사이에는 배포까지 직접 해봐야만 보이는 간극이 있다는 걸 경험했어요.
